# 專案工作守則

## 1. 基本原則

1. 本專案採用 Spec-Driven Development（SDD）：先形成可驗收規格，再修改產品程式碼。
2. 所有專案規格、決策、進度、測試結果與重大問題紀錄都放在 `docs/`。
3. 使用繁體中文撰寫專案文件、使用者可見文案與 Git 提交說明；程式識別字可使用英文。
4. 不得把「提案」當成已確認需求。未決事項必須保留狀態與理由。
5. 保留使用者既有內容；若需搬移、刪除或大幅改寫，應先保留來源或取得確認。

## 2. 規格驅動流程

每項功能依序執行：

1. 探索：整理問題、限制、使用情境與未知事項。
2. 規格：從 `docs/templates/feature-spec-template.md` 建立文件。
3. 確認：規格至少包含目標、非目標、行為、驗收條件與測試方式。
4. 實作：只實作已核准範圍；新發現的需求先回寫規格。
5. 驗證：執行自動測試、建置檢查與必要的桌面／行動裝置視覺驗證。
6. 紀錄：更新規格狀態及 `docs/logs/` 的階段紀錄。

## 3. 規格品質門檻

規格進入「已核准」前，必須能回答：

- 玩家或使用者獲得什麼價值？
- 正常流程與邊界情境如何表現？
- 哪些內容不在本次範圍？
- 如何客觀判斷完成？
- 桌面與手機操作是否都有定義？
- 是否影響效能、可存取性、存檔或既有遊戲狀態？

驗收條件優先使用 `Given / When / Then`，避免「運作正常」「畫面好看」等無法驗證的描述。

## 4. 遊戲專案特別守則

- 核心產品承諾是「遊戲因玩家死亡而逐漸同情玩家，並用世界觀內的荒謬事件作弊幫忙」。不得退化成一般難度選單或只調低數值。
- 死亡必須推進內容或喜劇期待，不能只造成重複挫折。
- 輔助事件應可測試、可重現，並避免因隨機性導致關卡無法完成。
- 桌面鍵盤與手機觸控是同等重要的輸入模式；任何關卡規格都需涵蓋兩者。
- 優先維持靜態網站部署能力，不引入非必要的後端服務。
- 不直接複製參考作品的關卡、美術、角色、音效或文案。

## 5. 程式與資產規範

- TypeScript 維持嚴格型別；避免以 `any` 略過設計問題。
- 將關卡資料、陷阱行為、援助規則與演出內容分離，避免把內容寫死在單一場景。
- 新增資產時記錄來源、授權與用途；來源不明的網路素材不得納入正式版本。
- 優先使用可壓縮、適合網頁傳輸的資產格式，並設定合理的效能預算。
- 不提交密鑰、憑證、個人資料、建置輸出或套件快取。

## 6. 驗證要求

每次功能提交前，依變更範圍至少完成：

- 型別檢查與正式建置。
- 受影響邏輯的自動測試。
- 核心流程的瀏覽器實際操作。
- 涉及介面或關卡時，檢查桌面與手機尺寸。
- 涉及物理／陷阱時，檢查重生、連續死亡與援助觸發不會卡死。

若無法執行某項驗證，必須在進程紀錄及交付說明中明確標示。

## 7. Git 規範

- 只使用本機 Git；除非使用者日後明確要求，不設定遠端、不推送。
- 提交前檢查差異，避免混入無關或使用者未授權的修改。
- 採用慣例式提交：`feat`、`fix`、`docs`、`refactor`、`test`、`chore`。
- 主旨格式：`類型: 本次更新重點摘要`。
- 重要提交本文使用分點，說明行為、規格與驗證結果。
- 每個可獨立回滾的階段建立一個提交；不得使用破壞性重置覆蓋使用者內容。

範例：

```text
docs: 建立 SDD 專案規格基線

- 定義產品願景與首個垂直切片提案
- 新增技術決策、待決問題及功能規格範本
- 建立代理守則與進程紀錄格式
```

## 8. 文件維護

- 文件內標示狀態、最後更新日期與關聯決策／規格。
- 規格變更時保留理由；重大技術決策使用 ADR。
- `docs/logs/` 記錄事實、結果與阻礙，不以日誌取代正式規格。
- 若程式行為與規格不一致，先判定哪一方需要修正，不可默默讓文件失效。

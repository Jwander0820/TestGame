# 產品待決問題

- 狀態：待討論
- 最後更新：2026-07-15

以下問題依「對第一個可玩版本的影響」排序。每題都附上建議預設值；若無特別偏好，可以直接接受預設值後繼續推進。

## 已確認（2026-07-15）

### Q1. 第一階段要做到哪裡？

- 決策：先做 1 個 3–5 分鐘的垂直切片，驗證操作、陷阱、死亡反應和喜劇節奏。
- 後續完整世界原始構想為 5 小關＋Boss；2026-07-17 因網頁小遊戲長度與製作負擔重新開放評估，詳見 Q11。

### Q2. 手機遊玩方向？

- 決策：遊戲固定採橫向邏輯畫面；手機直拿時顯示旋轉提示。

### Q3. 基礎操作複雜度？

- 決策：左、右、跳躍三鍵；不加入攻擊、衝刺與蹲下。

### Q4. 技術方案是否接受瀏覽器遊戲框架？

- 決策：採用 Vite + TypeScript + Phaser，產出仍是可部署的靜態網站。
- 說明：Phaser 是程式庫，不要求玩家安裝桌面引擎，也不代表需要後端。
- 決策文件：`docs/decisions/ADR-0001-browser-game-stack.md`。

## 尚待確認

### Q5. 美術方向？

- 建議：低解析度像素感比例與清楚輪廓，但不限制所有圖像必須逐像素繪製；使用可愛角色、明亮場景和略顯突兀的「系統介入」視覺。
- 待選：純像素、手繪卡通、幾何向量、混合風格。

### Q6. 死亡與援助狀態如何保存？

- 建議：使用瀏覽器本機儲存；一般重新整理保留進度，選單提供「重新開始世界」與「清除全部紀錄」。
- 待確認：玩家是否能重看已觸發的援助／彩蛋。

### Q7. 語言範圍？

- 建議：第一版只做繁體中文，但文案從程式邏輯分離，保留未來英文在地化能力。

### Q8. 喜劇語氣與分級？

- 建議：全年齡、嘴壞但不羞辱玩家；嘲諷指向遊戲系統和荒謬處境，而不是玩家能力或身分。

### Q9. 音效與音樂？

- 建議：垂直切片先加入必要操作／死亡／援助音效與一段可循環背景音樂；提供靜音，並遵守瀏覽器需玩家互動後才能播放聲音的限制。

### Q10. 最終靜態網站部署位置？

- 建議：開發階段保持平台中立，先確保 `dist/` 可部署；接近交付時再從 GitHub Pages、Cloudflare Pages、Netlify 等靜態平台選擇。

### Q11. 完整世界採 3+1、4+1 或 5+1？

- 目前傾向：縮為 3 小關＋Boss，或 4 小關＋Boss。
- 4+1 的候選笑點：第 4 小關使用全白、極簡或明顯擺爛的場景，讓世界在 Boss 前徹底放棄維持專業；仍需保證可讀性與可完成性，不能以未完成素材冒充笑點。
- 決策門檻：完成深化後第一關的真人試玩，再依首次完成時間、笑點密度、美術成本與後續機制提案定案。
- 狀態：使用者提出方向，尚未正式選定總關數。

# 2026-07-16：採用風險分層驗證策略

## 背景

使用者希望先完成程式碼與可維護性設計，後續再自行試玩並針對實際問題回報；不要求每次修改都進行高成本的瀏覽器或實機操作。

既有守則將「核心流程的瀏覽器實際操作」列為每次功能提交的固定項目，容易讓純重構、資料整理及已有自動覆蓋的小幅變更重複執行相同的手動流程。

## 決策

將 `docs/AGENT.md` 的驗證要求改為風險分層：

1. 共通基線使用型別檢查、受影響自動測試，以及必要時的正式建置。
2. 低風險且不改變行為的修改不強制操作瀏覽器。
3. 保存、輸入、物理、陷阱、援助及版面變更，優先建立針對性自動整合或幾何檢查。
4. 完整瀏覽器、手機尺寸與真人實機驗證集中於里程碑、大幅流程修改、自動測試無法覆蓋的問題，或使用者回報後的問題重現。

## 影響

- 日常開發優先改善模組邊界、資料與邏輯分離、可測試性及維護成本。
- 不把「未每次實機操作」視為缺陷；只要已完成與風險相符的自動驗證即可提交。
- 物理、保存及輸入等高風險行為仍需留下可重現證據，但可由穩定的自動整合測試承擔。
- 真人操作手感、實際手機相容性與主觀節奏保留到里程碑，由使用者試玩後再進行針對性調整。
